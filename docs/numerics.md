# Deterministic numerical implementation

The public representation is a signed 64-bit integer scaled by 2^16 or 2^32.
All potentially overflowing operations take place in unsigned arithmetic, in
checked signed arithmetic, or in two-/three-word unsigned accumulators. Signed
negative values are never left-shifted or right-shifted. Magnitude extraction
works at `INT64_MIN`, and unsigned-to-signed conversion is performed only after
range checking. There is no dependency on `libm`, compiler floating point
contraction, the host floating point rounding mode, or floating point registers.

## Arithmetic and conversions

Addition/subtraction check bounds before evaluating a potentially overflowing
signed expression. Multiplication forms a full unsigned 128-bit magnitude,
rounds its shifted result, and reapplies the sign with saturation. Division
shifts the numerator into 128 bits, divides by the unsigned denominator, then
compares the remainder to its complement for a nearest-even decision. This
avoids overflow in `2 * remainder`. The portable divider uses shifted subtraction;
the fast divider uses the host compiler's unsigned wide arithmetic/intrinsics.

The decimal parser never uses a floating point intermediary. It retains F+1
decimal fractional places plus a sticky bit. Every binary rounding midpoint at
F fractional bits terminates within that many decimal places, which lets the
parser distinguish exact ties even for very long inputs. Integer digits and
exponents are range-checked separately. String output repeatedly multiplies the
fractional remainder by ten, producing its exact terminating decimal.

IEEE input decodes the sign/exponent/fraction and shifts the significand with
nearest-even rounding. IEEE output finds the top magnitude bit, rounds to 24 or
53 significant bits, and encodes the exponent. These fixed formats never require
an IEEE subnormal on output. The byte APIs assemble/disassemble bytes explicitly.

The normative instruction semantics for the optional accelerators are described
by the [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html)
and Microsoft's [_umul128](https://learn.microsoft.com/en-us/cpp/intrinsics/umul128?view=msvc-170)
and [_udiv128](https://learn.microsoft.com/en-us/cpp/intrinsics/udiv128?view=msvc-170)
documentation. The portable implementations define matching results.

## Roots

`sqrt` uses restoring integer square root on `raw << F`. If the floor root is r,
the exact rounding test is `n - r*r > r`. There cannot be an exact halfway case
for integer n. `hypot` first sums full-width raw squares and uses the same test,
so large intermediates do not saturate before the root.

`cbrt` forms `abs(raw) << (2*F)`, finds its floor cube root by binary search, and
compares `(2*r + 1)^3` against `8*n` using a three-word accumulator. This defines
nearest rounding without an approximate seed or premature multiplication
overflow. Negative cube roots use the same magnitude calculation.

## Transcendentals

The bounded polynomial kernels use signed Q4.60 arithmetic. All polynomial
coefficients and range-reduction constants are integer constants. Reciprocal
factorials and reciprocal odd integers are generated by constexpr integer
arithmetic. Horner evaluation avoids divisions within polynomial loops.

| Functions | Algorithm |
| --- | --- |
| `sin`, `cos`, `tan` | Reduce the raw angle modulo pi/2 in unsigned Q128 using a three-word accumulator, select a quadrant, reduce the polynomial input to [0, pi/4], evaluate sine degree 17 and cosine degree 18. Tangent normally divides internal sine by internal cosine; within 2^-8 radians of a pole, it uses a wide reciprocal and a cotangent correction polynomial. |
| `atan`, `atan2` | Form a magnitude ratio <= 1; transform ratios above tan(pi/8) with `(x-1)/(x+1)`; evaluate the odd arctangent series through degree 49; restore the quadrant. |
| `asin`, `acos` | Compute the complementary leg using a wide integer square root, then use the internal atan2 kernel. |
| `exp`, `expm1` | Reduce by ln(2) to roughly [-ln(2)/2, ln(2)/2], evaluate degree 18, then scale by a power of two. `expm1` keeps its subtraction inside the wide accumulator. |
| `exp2` | Reduce in base two, multiply the fractional residual by ln(2), and use the exponential polynomial. Integer exponents have exact power-of-two behavior subject to rounding and saturation. |
| `log`, `log2`, `log10`, `log1p` | Normalize the magnitude into [1, 2], evaluate `2*atanh((m-1)/(m+1))` through degree 43, then restore the exponent in a wide accumulator. `log1p` adds one before normalization with unsigned headroom. |
| Noninteger `pow` | Multiply the wide internal logarithm by the exponent and pass the wide product directly into exponential range reduction. |

`tools/generate_constants.py` reproduces pi and logarithm constants using 110
decimal digits. The Q128 angle reduction limits accumulated phase error across
the full `real` range. Rounding a public `pi_v<T>` still changes the input angle:
`sin(pi_v<T>)` need not equal zero.

## Accuracy contract and measurements

The [full measured table](accuracy-results.md) compares the frozen results with
an independent 110-digit oracle. Errors there are measured in raw units, where
one unit is 2^−F. It is a reproducible finite test corpus, not a proof of a
universal ULP bound for every transcendental input. Each frozen result is checked
bit-for-bit independently of the oracle's accuracy tolerance.

The oracle tolerances are deliberately explicit:

| Family | Allowed error in raw units |
| --- | --- |
| Exact arithmetic/conversions, named rounding, roots, hypot | 0 |
| Sine/cosine, inverse trig, logarithms | 2 |
| Exponentials | `2 + ceil(abs(expected_raw) * 1e-16)` |
| Noninteger powers | `2 + ceil(abs(expected_raw) * 1e-16 * (1 + abs(exponent)))` |
| Tangent, `abs(tan(x)) <= 256` | `2 + ceil(2^F * (1 + tan(x)^2) * (abs(x)*2^-128 + 2^-54))` |
| Tangent, `abs(tan(x)) > 256` | `2 + ceil(2^F * (1 + tan(x)^2) * abs(x)*2^-128)`; tolerance is capped to the signed 64-bit maximum |

Integer power cases use an independent model of the documented sequence of
rounded multiplications, rather than claiming a single rounding of the exact
mathematical power. For noninteger powers the tolerance accounts for logarithm
error amplified by a large exponent. Tangent's tolerance accounts for the
derivative `1 + tan(x)^2`; close to a pole, small phase errors have large absolute
effects. A general small-ULP promise for such inputs would be misleading.

## Reference maintenance

`oracle.csv` is generated by Python arbitrary-precision integers, `Fraction`, and
mpmath 1.3.0 at 110 decimal digits. A fixed random seed and explicit boundary
cases make generation reproducible. Continued-fraction approximations of pi
also exercise extremely large angles close to tangent poles. The corpus includes
malformed/domain-error cases.
`results.csv` freezes the **portable scalar C++ implementation's** answers after
the independent oracle test succeeds. It is the cross-platform bit compatibility
contract. Its writer target unconditionally defines `FXP_PORTABLE_ONLY=1` and
`FXP_DISABLE_SSE2=1`, and the writer refuses to compile without these definitions.
Thus neither compiler-native wide arithmetic nor the SSE2 implementation can
generate the baseline, even when they are enabled for the rest of the build.

The original baseline used scalar operators with native wide integer arithmetic
enabled. Regeneration using the enforced standard C++ scalar backend reproduced
all 51,004 existing rows exactly; only the file's provenance header changed.
The optimized scalar implementation is tested against the same file. Batch
tests also feed its addition/subtraction rows directly through the SSE2 backend
when available and require exact equality, in addition to the aliasing tests.

Normal builds need neither Python nor mpmath. To deliberately create a new
reference version after reviewing a numeric algorithm change:

```sh
python3 -m pip install mpmath==1.3.0
python3 tools/generate_oracle.py
cmake --build build --config Release
./build/fxp_tests --gtest_filter=-Reference.ExactCrossPlatformResults
./build/fxp_reference_writer tests/reference/oracle.csv tests/reference/results.csv
python3 tools/accuracy_report.py > docs/accuracy-results.md
ctest --test-dir build --output-on-failure
```

With Visual Studio, use the executables in `build/Release`. Review all output
changes and validate the new files on the compiler/platform matrix. Never
regenerate reference outputs just to make a failing platform pass. Applications
requiring saved-state or network compatibility should pin the library version
and treat a changed raw result as a simulation compatibility change.
